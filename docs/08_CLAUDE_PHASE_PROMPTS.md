# KidGem Claude phase prompts

Use these after the master prompt. Attach the complete pack first. Each prompt is intended to produce changes in the repository, not just advice.

## Phase 1 Foundation and complete first lesson
Read the KidGem build documents and inspect the repository before changing it. Implement the Vite/React/TypeScript foundation, accessible responsive navigation, profile selector, locale dictionaries, validated curriculum data and a complete equal-groups lesson. Deliver its full Discover → Guided Try → Play → Practice → Challenge → Summary flow, versioned local persistence and a tested next-step recommendation. Run validation, tests and build. Inspect desktop/mobile screens. Update README and STATUS.md with exact commands, evidence and limitations. Do not stop at a landing page.

## Phase 2 Twelve lesson demo
Continue from STATUS.md without recreating the app. Implement the remaining eleven lessons required by document 01 using reusable games and schema-validated content. Label draft fixtures honestly; do not fabricate educator approval. Implement mastery, cosmetic reward idempotency, revision suggestions and parent evidence summaries. Make planned grade content visible without making it appear playable. Test every lesson and all edge cases from document 07. Report which acceptance IDs pass and what remains.

## Phase 3 Design and accessibility review
Review the actual KidGem build on phone, tablet and desktop. Improve hierarchy, Continue action, path order, younger/older themes, feedback, focus, reduced motion and EN/FR/BN rendering. Verify every link and control. Fix problems in code and provide before/after evidence where useful. Do not replace working games with decorative mockups. Run accessibility tools plus keyboard and screen-reader checks where available, and name any unperformed checks.

## Phase 4 Production accounts and backend
Inspect the existing adapter boundaries and implement the production API/database plan from document 05 using the owner-selected provider. If the provider is not selected, prepare provider-neutral contracts, migrations and tests and list the configuration decision; continue unrelated work. Add adult authentication, family-scoped records, server-validated attempts/rewards, export/deletion and authorization tests. Keep the static demo mode working. Do not deploy billable services or collect real child data before the owner completes the launch configuration and required review.

## Phase 5 Content publishing and coverage
Implement a protected draft/review/publish workflow with version history and a coverage dashboard. Add the next prioritized chapters from document 03 while retaining the narrow-objective lesson model. Validate answers and show exactly which educator/language reviews remain. Do not claim official alignment or trilingual completeness from generated content. Ensure old attempts remain interpretable after lesson changes.

## Phase 6 GitHub deployment preparation
Prepare a clean GitHub-ready repository with a working build/test workflow and a GitHub Pages deployment workflow for the static demo. Validate `/kidgem/` base paths, direct hash routes and assets. Add exact setup and rollback instructions. If the owner has not supplied a remote or authorized publication, stop at a reviewable deploy-ready state. Never invent a deployed URL or successful workflow run.

## Phase 7 Growth preparation
Implement the useful public skill/resource pages described in document 06 with truthful titles, metadata, readable content and direct links into the app. Document the transition from hash-routed demo to crawlable production URLs. Add a disabled analytics adapter and exact metric definitions. Draft adult-facing pilot questions and a launch checklist. Do not invent testimonials, learner counts, research outcomes or guaranteed search rankings.

## Continue after context runs out
Read docs/00_START_HERE.md, STATUS.md, the current repository and failing checks. Summarize the current milestone in five lines. Continue the next unfinished acceptance item without rebuilding completed work. Run relevant checks and update STATUS.md. Ask only for decisions that block dependent work; keep making progress on independent tasks.

## Fix a failed release gate
Use document 07 to reproduce the failure. Identify its cause, make the smallest maintainable correction, add a meaningful regression check if warranted and rerun relevant tests. Report actual evidence. Keep unresolved gates visible and do not remove a test merely to obtain a pass.
